03 — the text tower, and whether it is in the same space¶

Summary. Two towers of CLIP ViT-B/32 only share a space if they came from the same checkpoint and the projection was applied. The silent failure is real and common: take the 768-d pooled hidden state instead of the 512-d projected text_embeds and you get plausible numbers that mean nothing.

This notebook independently reproduces the retrieval gate that artist/tests/artist-clip-text.test.ts asserts, in Python, from the loaders — and compares. Two implementations agreeing is the evidence; one implementation asserting itself is not.

The published TypeScript numbers, on 500 stride-sampled works with usable titles:

measured chance ratio
P@1 within the 500-work pool 20.4% 0.2% 102x
P@10 within the 500-work pool 54.8% 2.0% 27.4x
P@10 against all 19,791 11.6% 0.051% 227x

Caveat carried forward from Stage 1, unchanged: the queries are museum titles, which are caption-like prose, which is exactly what CLIP was trained on. This measures a shared space. It does not measure that the encoder understands a work.

The pool, chosen the same way the test chooses it¶

Titles that are blank, Untitled, or shorter than four characters are dropped. That exclusion flatters the number — the short ones are Cup, Jar, Fan, Box, which are the generic queries many corpus images would answer equally well. So this is an upper bound, and it is stated as one.

def gate(rank, n_candidates, label):
    p1, p10 = (rank == 0).mean(), (rank < 10).mean()
    mrr = (1 / (rank + 1)).mean()
    c1, c10 = 1 / n_candidates, 10 / n_candidates
    print(f"{label}  ({n_candidates:,} candidates)")
    print(f"   {k.Reading('P@1 ', p1, c1)}")
    print(f"   {k.Reading('P@10', p10, c10)}")
    print(f"   MRR {mrr:.4f}")
    return p1, p10, mrr

py_pool = gate(rank_pool, N, "within the 500-work pool")
print()
py_all = gate(rank_all, len(order), "against the whole corpus")

Does the independent reproduction agree with the TypeScript gate?¶

It agrees exactly — all four deltas are 0.0000. That is a stronger result than expected and it is worth being precise about what it does and does not prove. It proves the two implementations select the same 500 works, embed the same strings through the same weights, and rank against the same deduped 19,791 rows: the export, the CSV join and the loader are all faithful. It does not double-check the encoder, because both paths call the same ONNX session. A tokenizer bug would show up identically in both columns.

Why no raw text-image cosine is ever printed alone¶

Text-image cosines live in a different band from image-image cosines — CLIP's learned logit scale puts them around 0.2–0.3. A reader who sees 0.28 next to an image-image 0.83 will conclude the text match is poor. It is not; it is a different ruler.
