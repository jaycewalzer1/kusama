# Stage 1 — the CLIP text tower

## 1.0 What this closes
Before tonight every question to the corpus had to start from an image. `resemblance.ts` had the
vision tower; there was no way to say a word to the corpus. There now is.

New files, all additive: `artist/clip-tokenizer.ts`, `artist/clip-text.ts`, `artist/clip-index.ts`,
`artist/search.ts`, `artist/tests/artist-clip-text.test.ts`, plus the `corpus search` command.
**No existing file changed except `studio/corpus.ts`** (four imports, one header line, one new
command). No hash moved; the gate confirms it.

## 1.1 Weights — the same checkpoint, which is the whole ballgame
CLIP's two towers are trained together with two learned projection matrices onto one shared space.
A text encoder from a *different* checkpoint returns 512 unit-length floats that are the right shape
and mean nothing against these images, and nothing anywhere would throw. So the text tower is the
same repo and revision as the vision tower already on disk:

| file | bytes | sha256 |
|---|---|---|
| `text_model.onnx` | 254,058,553 | `3f6571f5bad13a97c469c1622e1cfc4d9aef78b79fdbfcff804ca357bfada8cc` |
| `vocab.json` | — | `5047b556ce86ccaf6aa22b3ffccfc52d391ea4accdab9c2f2407da5b742d4363` |
| `merges.txt` | — | `9fd691f7c8039210e0fced15865466c65820d09b63988b0174bfe25de299051a` |

All three from `Xenova/clip-vit-base-patch32`, all three pinned in source and checked on load, all
three in gitignored `.models/`. **No API key, no credit, no network at query time.**

ONNX io, probed rather than assumed: **inputs `['input_ids']`, outputs `['text_embeds']`, `[n,512]`
float32.** `text_embeds` is POST-projection; reading the pooled hidden state instead (768-d) is the
standard way to get this silently wrong, and it is called out in the file.

## 1.2 There is no `attention_mask` input, and that is correct — MEASURED
The export takes `input_ids` only. That is not a defect: CLIP's text transformer is causally masked
and pools at the eos position, so nothing after the first eos can reach the vector. Rather than
argue it, `"a woodcut of a bird"` was embedded three ways — at its real length of **8 tokens**,
padded to 77 with eos, and padded to 77 with **zeros**:

```
padded-77(EOS) vs truncated : 1.00000000
padded-77(EOS) vs padded-0  : 1.00000000
```

Identical to eight decimal places. This is now a test (`embedTokens` exists only so it can be one).

## 1.3 The tokenizer was written by hand, and it is exactly right
`@huggingface/transformers` would have dragged in a **second onnxruntime** beside the
`onnxruntime-node` this repo already loads. Two native runtimes in one process is a worse problem
than 150 lines of byte-level BPE, so the BPE was written: `bytes_to_unicode`, CLIP's own split
regex, the `</w>` word-final convention, and the merge table (**49,408 vocab entries, 48,888
merges** after skipping the `#version: 0.2` header).

The positive control is exact:

```
a photo of a cat -> [ 320, 1125, 539, 320, 2368 ]   (published ids, matched)
```

Negative control: `woodcut` is **not in the vocabulary** and BPE-splits to `[3269, 3032]` rather
than vanishing into an unknown token — which is what would have happened silently, to every
printmaking query, had the merge loop been wrong. `appliqué` and `Œuvres`, both real museum medium
strings that a previous TF-IDF run mangled, survive the byte mapping and do **not** collide with
their unaccented spellings.

## 1.4 The index loader deduplicates, because Rule 7 says the loader is where it belongs
`artist/clip-index.ts` joins `corpus/clip.f32` to the manifest by sha256 and is the single door
every similarity in this stage goes through:

```
19,807 rows in the file -> 19,791 entries
   98 duplicate manifest rows collapsed (kept as `aliases`, not dropped silently)
    0 zero rows (no recorded encoder failures)
```

19,791 is the same number the deduped `resemblance` baseline reached from the other direction. The
work that names an image is the **lowest id** among those sharing the bytes, so the choice does not
depend on manifest order. Image rows sampled 100-at-a-stride are unit length to **1.000000**, so a
dot product is a cosine and nothing renormalises at query time.

## 1.6 What this does NOT show, said plainly
- **The gate is measured on titles, and a title is museum prose.** *The Girls on the Bridge* names
  what is depicted; `Woodblock for The Urus or Wild Bull, from A General History...` names a
  provenance. Some share of the 54.8% is CLIP reading a caption-like string against a picture, which
  is exactly what it was trained on and is a fair test of a shared space — but it is **not** a
  measurement of aesthetic description, and no number here says the encoder understands a work.
- **331 of 19,791 works (1.7%) were excluded from the query pool, and the exclusion flatters the
  number.** I wrote the filter expecting it to be mostly `Untitled`. It is not: **only 16 are
  literally "Untitled". 315 are titles shorter than four characters** — `Cup`, `Jar`, `Fan`, `Box`.
  Those are precisely the *generic* queries that many corpus images would answer equally well, so
  dropping them removes hard cases, not degenerate ones. The honest reading is that P@10 would be
  somewhat below 54.8% on the unfiltered pool. It is still 27x chance with a lot of room.
- **No corpus image reaches the artist through any of this.** `corpus search` is a lookup for a
  person. Stage 5 is where an influence would enter a run, and it has not happened yet.

## 1.7 `corpus search`, and why no raw cosine is ever printed alone
CLIP's text-image cosines live in a narrow band around 0.20-0.35 — the learned logit scale is
thrown away by the export — so "this work scored 0.33" is nearly contentless. Every hit therefore
carries its **z-score and percentile within that query's own distribution over the entire corpus**,
which costs nothing because the full scan has already computed every score. Same discipline as
`artist envelope` and `artist resemblance`, same reason: a number whose real range is 0.15-0.40,
printed as though it ran 0 to 1, is a lie with four decimal places on it.

```
$ node dist/studio/corpus.js search "a woodcut print" -k 6
searched 19791 distinct corpus images; this query's scores over all of them:
  mean 0.2025 sd 0.0297 min 0.1105 max 0.3304

  cos      z     pct     id            classification / title
  0.3304   4.31   99.99  aic-88398     woodcut | The Girls on the Bridge
  ...
museum crossing (share of these hits vs share of the searched set):
  aic   83.3% of hits    34.3% of corpus
  met    0.0% of hits    49.6% of corpus
```

The **museum-crossing column is per-query**, which is Stage 7's aggregate claim made checkable one
query at a time. On `"a woodcut print"` it is stark and it is *not* a bug: 34.3% of the corpus is
AIC and 83.3% of the hits are, because AIC is the museum that actually holds and catalogues Western
prints. That is a fact about the collections, and the column exists so it can be seen rather than
averaged away.

`--image` works too, in the same space, and gives a much better-founded reading than
`artist resemblance` could — that compared a plate against **50** works, this against all 19,791:

```
$ node dist/studio/corpus.js search --image out/condition-withheld/final.png -k 5
  mean 0.5372 sd 0.0591 min 0.2557 max 0.7995
  0.7995   4.44   99.99  aic-65821   painting | Composition (No. 1) Gray-Red
```
