## 1.1 Weights — the same checkpoint, which is the whole ballgame
CLIP's two towers are trained together with two learned projection matrices onto one shared space.
A text encoder from a *different* checkpoint returns 512 unit-length floats that are the right shape
and mean nothing against these images, and nothing anywhere would throw. So the text tower is the
same repo and revision as the vision tower already on disk:

| file | bytes | sha256 |
|---|---|---|
| `text_model.onnx` | 254,058,553 | `3f6571f5bad13a97c469c1622e1cfc4d9aef78b79fdbfcff804ca357bfada8cc` |
| `vocab.json` | — | `5047b556ce86ccaf6aa22b3ffccfc52d391ea4accdab9c2f2407da5b742d4363` |
| `merges.txt` | — | `9fd691f7c8039210e0fced15865466c65820d09b63988b0174bfe25de299051a` |

All three from `Xenova/clip-vit-base-patch32`, all three pinned in source and checked on load, all
three in gitignored `.models/`. **No API key, no credit, no network at query time.**

ONNX io, probed rather than assumed: **inputs `['input_ids']`, outputs `['text_embeds']`, `[n,512]`
float32.** `text_embeds` is POST-projection; reading the pooled hidden state instead (768-d) is the
standard way to get this silently wrong, and it is called out in the file.

## 1.2 There is no `attention_mask` input, and that is correct — MEASURED
The export takes `input_ids` only. That is not a defect: CLIP's text transformer is causally masked
and pools at the eos position, so nothing after the first eos can reach the vector. Rather than
argue it, `"a woodcut of a bird"` was embedded three ways — at its real length of **8 tokens**,
padded to 77 with eos, and padded to 77 with **zeros**:

```
padded-77(EOS) vs truncated : 1.00000000
padded-77(EOS) vs padded-0  : 1.00000000
```

Identical to eight decimal places. This is now a test (`embedTokens` exists only so it can be one).

## 1.3 The tokenizer was written by hand, and it is exactly right
`@huggingface/transformers` would have dragged in a **second onnxruntime** beside the
`onnxruntime-node` this repo already loads. Two native runtimes in one process is a worse problem
than 150 lines of byte-level BPE, so the BPE was written: `bytes_to_unicode`, CLIP's own split
regex, the `</w>` word-final convention, and the merge table (**49,408 vocab entries, 48,888
merges** after skipping the `#version: 0.2` header).

The positive control is exact:

```
a photo of a cat -> [ 320, 1125, 539, 320, 2368 ]   (published ids, matched)
```

Negative control: `woodcut` is **not in the vocabulary** and BPE-splits to `[3269, 3032]` rather
than vanishing into an unknown token — which is what would have happened silently, to every
printmaking query, had the merge loop been wrong. `appliqué` and `Œuvres`, both real museum medium
strings that a previous TF-IDF run mangled, survive the byte mapping and do **not** collide with
their unaccented spellings.

## 1.4 The index loader deduplicates, because Rule 7 says the loader is where it belongs
`artist/clip-index.ts` joins `corpus/clip.f32` to the manifest by sha256 and is the single door
every similarity in this stage goes through:

```
19,807 rows in the file -> 19,791 entries
   98 duplicate manifest rows collapsed (kept as `aliases`, not dropped silently)
    0 zero rows (no recorded encoder failures)
```

19,791 is the same number the deduped `resemblance` baseline reached from the other direction. The
work that names an image is the **lowest id** among those sharing the bytes, so the choice does not
depend on manifest order. Image rows sampled 100-at-a-stride are unit length to **1.000000**, so a
dot product is a cosine and nothing renormalises at query time.

## 1.7 `corpus search`, and why no raw cosine is ever printed alone

thrown away by the export — so "this work scored 0.33" is nearly contentless. Every hit therefore
carries its **z-score and percentile within that query's own distribution over the entire corpus**,
which costs nothing because the full scan has already computed every score. Same discipline as
`artist envelope` and `artist resemblance`, same reason: a number whose real range is 0.15-0.40,
printed as though it ran 0 to 1, is a lie with four decimal places on it.

# Stage 2 — influences: an artist's background as weights over the corpus

## 2.0 What this closes
Stage 1 made the corpus addressable in words. Stage 2 asks the first artist-shaped question of it:
**given a position file, which 48 of 19,791 works is this artist working out of?** The answer is
written to `aesthetic/influences/<id>.json` (the queries) and `<id>.resolved.json` (the works,
centroid, axes and statistics), both tracked, both content-hashed as `influencesHash`.

**Zero model calls.** The queries are cut out of the position file with a regex and a sentence
splitter; the retrieval is the local CLIP text tower from Stage 1. Nothing has *read* anything.

## 2.1 How a position becomes queries — verbatim text, no interpretation
| source | what it takes | weight | k |
|---|---|---|---|
| `lineage` | each entry's `ref` string as written | 1.0 | 12 |
| `worldview` | each sentence of the paragraph, split on `.!?` | 0.8 | 12 |
| `commitment` | each commitment's `why` | 0.6 | 8 |
| `avoid` | cliches + prohibition `why`s | down-weight, never removal | — |

Counted on disk, not assumed: **19 queries for each of the three positions** (6 lineage, 7-8
worldview, 5-6 commitment) and **8-11 for the four pack elements**. **0 queries truncated** past
CLIP's 77-token context and **0 empty** — every query returned something above `minCosineToQuery`
0.20. That the worldview sentence split was needed at all is measurable: the un-split paragraphs run
well past 77 tokens, and CLIP would have embedded the first two clauses and discarded the rest in
silence.

`avoid` is a **multiplier on weight**, `max(0.5, 1 - max(0, cos - floor) * 2.5)`, never a filter.
Penalties actually bite: the top of `interference` runs 0.71-0.86, so the prohibition text is moving
the ranking rather than decorating it.

## 2.2 THE BUG THAT MAKES THIS STAGE HONEST — the PCA was returning noise
`corpus influences resolve withheld` printed:

```
axis 0 — 10.2% of the set's variance
axis 1 — 22.0% of the set's variance
axis 2 —  4.2% of the set's variance
```

Principal axes are ordered *by construction*. Axis 1 cannot explain more than axis 0. Nothing else
in the output looked wrong — three axes, real works with plausible captions at both ends of each,
labels drawn from real catalogue columns. **The only thing that gave it away was arithmetic.**

Cause: `principalAxes` tested convergence with `1 - |dot(next, v)|` where `next` is unit-length but
the **seed `v` was not** — 512 uniform draws have norm about 6.5, so the dot product exceeded 1,
`moved` came out **negative**, and `moved < 1e-9` broke the loop after a **single power step**. Every
axis was one multiplication away from the random start vector.

Verified against ground truth rather than by inspection: the 48x48 Gram matrix run to 5,000
iterations in float64 gives `0.2747 / 0.0739 / 0.0614`; the fixed implementation gives
`0.2747 / 0.0739 / 0.0614`. Before the fix it gave `0.1212 / 0.1922 / 0.0320`.

A second defect was fixed at the same time: `principalAxes` was being handed the set's `centroid`,
which is **unit-normalised** because it doubles as a retrieval query. Centring on it is not PCA. The
mean is now computed inside the function and the parameter is gone, so the mistake is unavailable.

`artist/atlas.ts` has its own `principalAxes` and **is not affected** — it has no early-exit
convergence test and always runs all 200 iterations. The published map numbers (metadata PCA 34.0x,
CLIP PCA 5.6x) stand.

The regression test is `PCA axes are ordered — explained variance never increases`. It needs no
corpus and no ground truth, because the property is true by construction.

## 2.3 The extremes operator, and where it stops
Walk out from the centroid along each axis in steps of half the set's own radius, and ask the corpus
what is nearest at each step. The walk stops when the nearest work falls below the corpus's own
median pair similarity (0.6428), and a 12-step cap guarantees termination regardless.

Which of the two stopped it is now **recorded and printed** (`endedPlus` / `endedMinus`), because it
changes what the output means. Before the PCA fix, walks along noise directions mostly ran into the
step cap; with real axes, **all six walks on `withheld` terminate on the corpus hull** (3-10 steps).
A walk that ends on the cap is reporting a direction the corpus keeps answering, and should be read
differently from one that ran out of corpus.

## 4.1 The projection is not refitted, and that was the whole design decision

The obvious implementation appends the plate vectors to the 19,791 corpus vectors and runs UMAP over
19,808. That is wrong in three ways at once and none of them are visible on the resulting page:

- every corpus point moves, so the overlay page and the corpus page are **different maps** that look
  the same;
- a plate can **create** the cluster it appears to have landed in, and nothing distinguishes that
  from landing in an existing one;
- two trajectories need two corpus maps, and neither page would say so.

So the corpus coordinates are frozen. A new point goes at the **cosine-weighted average of the 2D
coordinates of its 20 nearest corpus works in the full 512-d space**. The map is a fact about the
corpus; the overlay is a reading of where something falls in it.

## 4.2 The finding: placement recall is 1.5%, and it was expected to be ~100%

I wrote the k=20 row of the fidelity table with the label `CIRCULAR — this is the k the placement
used`, on the reasoning that a point placed at the centre of twenty works must land among those
twenty. **It measured 0.0147.** So I wrote `placementRecall()` to ask the question directly rather
than inferring it from the fidelity table:

> Of the 20 corpus works a plate was placed FROM, how many are among the 20 corpus points nearest
> the placement on the page?

**1.5%** for `condition-withheld`, **2.9%** for `openai-withheld`.

The mechanism is that **UMAP preserves adjacency and not distance**. Twenty works that sit together
in 512 dimensions can be scattered across several regions of a UMAP, and the centroid of scattered
points is in the gap between them — a region whose own inhabitants may be nothing like the twenty.
The placement is not arbitrary: `meanCosine` says the plate genuinely is near those twenty in the
space. It is that **the page cannot show it**.

The `CIRCULAR` label was removed from the CLI, the page and the type (`Fidelity.independent` ->
`Fidelity.wider`), because every row of that table turned out to be a real measurement. The finding
is printed in the page footer, in the CLI output, and in `THURSDAY.md`'s "what not to claim".

Two tests in `artist/tests/artist-overlay.test.ts` pin this rather than leaving it as prose: one
fixture where four mutually-near works sit at the four corners of a map and the placement lands
dead-centre on four works it is nothing like (recall **0**), and a control on a metric map where the
same code returns recall **1**. If a future change makes recall come out high on the first fixture,
the placement stopped being a centroid and the page's caveat became wrong.

|---|---|---|---|
| k=20 | 0.0147 | 0.0010 | 14.6x |
| k=100 | 0.0824 | 0.0051 | 16.3x |
| k=500 | 0.2885 | 0.0253 | 11.4x |

Every row is above chance and every row is low. The honest reading is the one on the page: a plate is
in the right **region** and is not necessarily beside the works it resembles.

Anchoring: the placed points sit at mean cosine **0.7807** to the 20 works they were placed from
(0.7406..0.8158), and the weights across those 20 differ by only **1.070x**. That last number matters
more than it looks: CLIP cosines live in a narrow cone, so the "cosine-weighted average" is very
nearly the **plain centroid** of the twenty. The weighting is not doing work, and the page says so
rather than implying a pull toward the nearest.

`openai-withheld` is the weaker anchor: mean cosine **0.6848** with a much wider range
(0.5701..0.8163), i.e. some of its plates are near nothing in the corpus.

## 4.4 The interpolation trap, stated on the page

A placed point **cannot leave the hull of the corpus's own coordinates**. A plate that resembles
nothing does not fly off the edge — it lands in the middle, at the centroid of twenty things it is
equally unlike, which on screen is indistinguishable from a plate that belongs there. `meanCosine` is
the only thing that separates the two cases, so it is reported per point in the hover and in
aggregate in the footer. A test asserts the hull property directly.

## 4.5 NOTHING MEASURED: there is no path

The brief asked for "plates as a connected path step 0 -> final". **The plates are drawn as points
and not joined.** No run has ever persisted a plate per MAKE step (the same gap Stage 3 reported).
What exists is one final plate and sixteen sketches, and sketches are alternatives considered at one
moment rather than a canvas over time. Joining them would draw a trajectory this project has never
recorded. `Landmark.step` exists and is `null` for every landmark today; `pathOf()` joins only
landmarks with a non-null step, so a run made after Stage 5 produces a real path with no change here.

## 4.6 An unrelated correction the stage forced: the map was double-counting 98 works

`clipSpace()` in `studio/corpus.ts` read `corpus/clip.f32` itself and joined by sha256, which meant
the atlas had **19,889 points over 19,791 distinct images** — the 98 rows that share bytes (one knife
and fork, shot once, catalogued twice) each appeared twice at the same coordinates. It now goes
through `loadCorpusEmbeddings()`, the same deduping loader everything else uses, so `entries[i].row
=== i` by construction and the overlay's row indices mean the same thing everywhere.

**I predicted this would lower `preservation` and `composition`, and it raised them.**

| | before (19,889) | after (19,791) |
|---|---|---|
| 20-neighbourhoods preserved / chance | 0.3232 / 0.0133 = 24.2x | 0.3348 / 0.0133 = **25.1x** |
| same museum (chance) | 55.4% (39.0%) | **55.9%** (38.9%) |
| same kind (chance) | 3.6% (0.3%) = 11.6x | **3.8%** (0.3%) = **14.5x** |

**These half-point moves are not attributable to the dedupe.** `evenSample` takes a stride over the
list, so a list 98 shorter is a *different* 1,500 works, and UMAP was refit over 98 fewer rows. Two
things changed and one number moved; that is not an attribution. The dedupe is here because it is
correct, not because it moved a number. The stale 24.2x / 55.4% figures were corrected in
`THURSDAY.md` §5.

While correcting them I found a second inconsistency that is **not** a bug and is a trap:
`THURSDAY.md` said appearance neighbours are 55.4% same-museum, notebook 02 says **66.3%**. Both are
right — 55.9% is over the atlas's 1,500-work stride sample, 66.3% is over the whole corpus. This is
rule 6's "a percentile is a fact about a pool" in a second costume. `THURSDAY.md` now carries both
with the pools named and an instruction not to put them in one sentence.

# Stage 5 — the corpus reaches the artist, and stops before the environment

## 5.0 What this closes

Every stage before this one measured the corpus. None of it had ever been in front of an artist. The
line in every previous report — *"no corpus image has ever reached an artist prompt"* — is no longer
true, and this stage is the only reason it is not.

What now exists: an optional L5 document (`artist/influence-doc.ts`) carrying a resolved set into
FIND and SKETCH as catalogue text plus up to eight real museum JPEGs; a tenth, **optional**
`envVersion.influencesHash`; a `--influences <id>` / `--influences-in-make` pair on `artist run`; a
plumbing run driven end to end with the model unplugged; and a model-free `corpus influences lens`
that reads any condition through a shelf **against the corpus as a baseline**.

Zero model calls. $0.00.

## 5.1 The hash rule, and the direction of drift that nearly went unnoticed

`OBSERVATION_HASH` is over the **source bytes** of `artist/observation.ts` and `artist/schemas.ts`.
One word added there declares every trajectory ever collected to be from a different environment.
So the block is built in its own module and **appended by the phases**, never interleaved by the
serializer. A run without the layer sends bytes identical to a run from before this file existed, and
`artist-influences-in-loop.test.ts` asserts that observation-for-observation, plus the absence of any
`influence`-shaped key in the `trajectory-start` line.

`influencesHash` is spread in, not assigned:

```ts
...(influencesHash ? { influencesHash } : {}),
```

`influencesHash: undefined` would be a different thing — `Object.keys` reports it, so `envDrift`
would iterate a field whose current value is undefined and call every run that *does* carry one
drifted.

The typechecker then caught a real hole rather than a style problem. `envDrift` skipped any field the
record did not carry, which is what makes the field additive; but that also silently covered the
**opposite** direction — a run recorded *with* influences, replayed *without*, would report no drift
while every observation differed by 8,256 characters. Fixed with an `ABSENT = '(absent)'` sentinel,
so:

| recorded | current | reported |
|---|---|---|
| absent | absent | — |
| absent | present | — (this is what "additive" means) |
| present | absent | **drift**, `current: '(absent)'` |
| present | different | **drift** |

That fix immediately failed `gate 1: the trajectory replays exactly`, and the failure was
instructive: `envDrift` is called with the **whole `trajectory-start` line** as `recorded` — a
`StartLine & Partial<EnvVersion>` carrying `id`, `positionId`, `briefId`, `mode` and a dozen more —
so a loop over `Object.keys(recorded)` reports every one of those as a field the environment has
lost. The key set is now `Object.keys(current)` plus an explicit
`OPTIONAL_FIELDS = ['influencesHash']`, and `recorded`'s keys are never iterated.

## 5.2 What the artist is actually shown — facts, with exactly one imperative

The whole experiment is whether an artist that has *seen* a lineage makes different work. A prompt
that says "take inspiration from these" answers that question by assuming it. So the block states
what is in the set and what the axes measured, in the indicative, and the one line that comes close
to a direction is a prohibition. `artist-influence-doc.test.ts` holds six banned regexes against it
(`/inspired by/i`, `/in the (style|manner) of/i`, `/work in this/i`, and so on).

The axis labels are the strongest case for this rule. `calligraphy -> furniture; aic -> met` is a
description of what a principal axis of this set actually separates, derived with no model. Handed
over as a fact it is evidence about the set. Rewritten as "move along the calligraphy/furniture axis"
it is aesthetic direction — the thing `aestheticDirection` exists to keep out of L2.

The real `withheld` block, verbatim numbers, **every one against its baseline**:

| what the block tells the artist | the set | chance |
|---|---|---|
| members resemble each other | 0.6416 | 0.6428 (corpus median pair) |
| pairs from one museum | 37.5% | 39.0% |
| flat (2D) work | 50.0% | 14.7% |

Two of those three are **at or below chance, and the block says so in those words** ("A set at or
below that number is a set that shares a subject rather than a look"). The artist is handed the
null, not a curated highlight. Axes: `calligraphy -> furniture; aic -> met` (27.5% of variance),
`lace -> chalk; met -> aic` (7.4%), `tomb pottery -> textile` (6.1%).

Block: **8,256 characters**, 48 catalogue entries, 8 JPEGs (1,981,876 base64 bytes ≈ 1.45 MB ≈ 4,500
image tokens). `influencesHash c2cb1a4946592065afa02f5e7f0e1942543e9b47b08a7a9ce5810d73572a2004`.

## 5.3 Where the block goes, and the three places it does not

| phase | block | pictures | why |
|---|---|---|---|
| FIND | yes | **8** | the one phase whose job is to decide what is difficult here, before anything is drawn |
| SKETCH | yes | none | same works, named; re-attaching 8 images to 9 sketch calls is ~40,000 input tokens to say the same thing nine times |
| MAKE / REPLAN | **no**, unless `--influences-in-make` | none | see below |
| DESCRIBE / TRANSCRIBE / AUDIENCE | **never** | never | see 5.4 |

MAKE is off by default and the reason is not token cost. FIND and SKETCH happen before there is a
picture; MAKE happens with one in front of the artist. A shelf of other people's work held up beside
a canvas mid-piece is the condition under which *derivation* turns into *quotation* — which is
precisely what `judge.ts` grades, and which it would then be grading as a pressure the environment
applied. `--influences-in-make` is the other arm, to be compared, not assumed better.

The `thumbnails` argument to `withInfluences` is **the number of pictures the caller will attach**,
not a display preference: the block's heading names the count and says the pictures are attached to
*this message*. FIND passes 8; SKETCH, ACT and REPLAN pass 0 and the heading changes to "No pictures
are attached to this message." This is the same defect `framesOf` already throws on in `act.ts`.

**A doc comment of mine was a lie for about twenty minutes.** It claimed the text count and the
payload count could not drift, while `influenceSection` counted works with an `imagePath` and
`influenceImages` skipped files not on disk. On a fresh clone — `corpus/images/` is 3 GB and
untracked — the manifest resolves and no pixel does, so the block would have said "the first 8 are
attached as images" over a payload of none: the artist told to look at something that is not there.
Both now derive from one `shownWorks(doc, n)` that filters on `existsSync`. The consequence is that
`InfluenceDoc.hash` depends on which pixels this machine has, which is correct rather than
unfortunate — two runs shown different numbers of pictures were shown different things.

## 5.4 The assertion that matters most — the environment stays blind

The environment's read of the plate is the only unbiased signal in the loop. A describer that knew
the artist had been shown eight museum textiles is a describer that can be led, and every reward
computed from it would be measuring the prompt. So `artist-influences-in-loop.test.ts` walks **every
env call from both influenced runs** and asserts the JSON contains neither the block's framing nor
**any influence work's title of 12 characters or more** — not just the wrapper, the works themselves.
A describer handed the titles could name a textile because it was told about one rather than because
it saw one.

This is the assertion that would fail first if the block were ever moved into `observation.ts`, where
the env calls would pick it up.

## 5.6 `corpus influences lens` — and it returns NOTHING MEASURED, three times out of three

Ranking 48 works by cosine to a phrase always produces a first-place work. It produces one for a
phrase about textiles and it produces one for a phrase about nothing, and the two look identical on
the page. So every ranking this command prints is accompanied by the same query's distribution over
**all 19,791 distinct works**, and the headline is not "which work is nearest" but "is this set
nearer to this condition than a work drawn at random". The floor is ±2 sd, chosen before looking at
any result.

Three conditions read through `withheld`:

| condition | set mean | corpus mean ± sd | z | verdict |
|---|---|---|---|---|
| "Two million slips of paper, each one a claim someone made about what happened to them." | 0.2182 | 0.1685 ± 0.0291 | **+1.71** | NOTHING MEASURED |
| "woven cloth, linen and thread" | 0.2428 | 0.2164 ± 0.0274 | **+0.97** | NOTHING MEASURED |
| "a photograph of a modern sports car on a racetrack" | 0.1660 | 0.1417 ± 0.0252 | **+0.96** | NOTHING MEASURED |

Read the last two rows together, because they are the finding. The `withheld` set's top hits are
*Length of Very Sheer Linen Cloth*, *Coverlet*, *Hand-woven Tablecloth* — and by set-mean z, this
shelf is **no more "about woven cloth" (+0.97) than it is "about sports cars" (+0.96)**. The nearest
works sit at p99, and the set as a whole sits inside the band. A position's influence set is not
selected for any particular brief, so this is the expected answer and not a defect; what would have
been a defect is printing the p99 ranking on its own and letting the reader supply the significance.

The command prints the ranking anyway — a refusal to draw a conclusion is not a refusal to show the
data — under an explicit "it is not evidence that the condition found them", and closes by saying
which ruler the numbers are on (a text-image cosine of 0.30 is a high one; 0.6428 is the
*image-image* median and does not apply).

Two things in `lens.ts` are defensive rather than decorative:

- **`sentences()` first, then averaged.** CLIP's context is 77 tokens including the specials, so a
  condition of any length is silently cut in half by the tokenizer. But `sentences()` drops anything
  under 12 characters, which is right for splitting a worldview and wrong for a query someone types —
  "lace" is a condition, not an empty text — so a text the splitter rejects entirely is encoded
  whole.
- **The width is read from the matrix, not from `rowAt`'s 512 default.** A mismatched width does not
  throw: `subarray` clamps, every dot product returns 0, and the result is sd 0 and z 0 — which
  renders as a *clean* NOTHING MEASURED. A bug wearing the costume of an honest null is the one
  failure this module exists to prevent, and the fixture corpus (8 dimensions) caught it.

## 5.7 `artist derive-themes` — `BLOCKED: credit`

The model-calling half of theme derivation — asking the artist what it makes of these works given
this condition — is not built, because it cannot be tested. Unblocking command, when credit exists:

```
export OPENAI_API_KEY=...   # or ANTHROPIC_API_KEY
node dist/studio/artist.js run withheld two-million-slips --influences withheld --seed 4242 \
  --out out/influenced-withheld
```

Note there is no `derive-themes` subcommand to write first. The block already puts the works in front
of the artist at FIND, and FIND's schema already asks what is difficult here; a separate
theme-derivation call would be a second, unvalidated place for the model to summarise a shelf it has
already been shown. If the run shows FIND is not enough, that is the evidence for building it.

## 5.8 `--corpus-distinct <cosine>` — NOT BUILT, and the numbers are why

The brief asked for a finish gate that refuses a piece too near a corpus work. I measured before
building, over the 52 plates already embedded in Stage 3:

| directory | plates | max cosine to nearest corpus work | median | min |
|---|---|---|---|---|
| `condition-withheld` | 17 | 0.8582 | 0.8212 | 0.7898 |
| `openai-withheld` | 17 | 0.8508 | 0.6878 | 0.6101 |
| `first-withheld` | 18 | 0.8430 | 0.7222 | 0.5984 |

Against the corpus's own internal distribution — min 0.1555, **median 0.6428**, max 0.9685 — a plate
sits about as near its nearest corpus work as two random corpus works sit to each other. The existing
`COPY_COSINE = 0.95` would never fire on any of the 52. A threshold at 0.86 would refuse nearly every
plate this project has ever made, including both finals.

There is no defensible number, so there is no knob. Shipping one would mean shipping a setting whose
only honest default is "off" and whose every other value is arbitrary — and the gate's refusals are
recorded in the trajectory as if the environment knew something. Recorded here instead, with the
distribution, which is the actual deliverable.

## 5.10 Things I decided without asking, in this stage

27. **`--influences-in-make` is deliberately NOT part of the run id.** The id carries what the artist
    *is* — position, brief, seed, control arm, element pack, and now which shelf it was shown — not
    how the driver was run. `showCanvas`/`--blind`, the older ablation, is absent for the same
    reason: both arms go to different `--out` directories, and folding every switch into the id would
    stop a resumable grid recognising a cell it had already done. The arm is recorded in the log
    instead, and a test pins `on.id === inMake.id` with that reasoning attached.
28. **A missing set is an error, not an empty document.** An artist told it has looked at nothing is a
    different experiment from an artist not told anything, and silently becoming the second would
    make a typo in `--influences` indistinguishable from the layer being off. Tested.
29. **JPEG passes through unchanged.** `PolicyImage.mediaType` is now `'image/png' | 'image/jpeg'`;
    both adapters hand it to the provider verbatim. Re-encoding museum bytes to PNG to satisfy a type
    would make what the run saw differ from what is on disk, for nothing.
30. **`corpus lens` lives under `influences`, not at top level.** It reads a condition *through a
    resolved set*; without one there is no set mean and so no z, and the ranking alone is the thing
    this whole module exists to refuse to print.
